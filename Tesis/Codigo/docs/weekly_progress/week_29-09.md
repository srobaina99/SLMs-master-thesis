### 2. **Scalable llama.cpp Architecture** 🏗️

**Objective:** Create reusable infrastructure for all future model migrations

**Design Pattern:**
```
BaseModelWrapper (abstract)
    └── LlamaCppBaseWrapper (abstract, reusable)
        ├── Qwen3LlamaCppWrapper ✅
        ├── Qwen2LlamaCppWrapper ✅
        ├── TinyLlamaLlamaCppWrapper ✅
        └── [Future models: SmolLM, Phi-3, Gemma]
```

**Key Features:**
- **Reusable base class:** Handles model loading, logit_bias, response extraction
- **Model-specific implementations:** Only 3 methods required per model:
  - `_format_prompt()`: Chat template formatting
  - `_get_stop_tokens()`: End-of-generation markers
  - `_extract_response()`: Output cleaning
- **Automatic integration:** Drop-in replacement for existing wrappers

**Files Created:**
- `src/evaluation/experiment_framework/models/llamacpp_base.py` (269 lines)
- Documented common chat templates (ChatML, Llama2, Gemma)

### 5. **Model Migration: TinyLlama-1.1B** ✅

**Date:** October 4, 2025

**Context:** TinyLlama already used llama.cpp, but with legacy wrapper. Refactored to match new architecture.

**Process:**
1. ✅ Downloaded official `TheBloke/TinyLlama-1.1B-Chat-v1.0-GGUF` (Q4_0, 608MB)
2. ✅ Created `TinyLlamaLlamaCppWrapper` (custom TinyLlama template)
3. ✅ Updated experiment framework integration
4. ✅ Integration test: All 4 intervention combinations passed

**Performance Impact:**
- **Before (Transformers):** ~5-10s per response, ~2.5GB memory
- **After (llama.cpp):** **1.3-3.1s per response**, **~600MB memory**
- **Speedup:** **3-5x faster**, **76% less memory**

**Validation:**
```
✅ Model loaded successfully in 0.9s
✅ Generated response (2.35s) - Control
✅ Weighting works (1.34s) - 493 vocab words
✅ Context prompting works (3.13s)
✅ Both interventions work (1.41s)
```

**Why This Had Such Impact:**
1. **Quantization:** float16 (2 bytes/param) → Q4_0 (0.5 bytes/param) = **4x less data**
2. **Native code:** Python/PyTorch → C++ core = **no interpreter overhead**
3. **Metal optimization:** Generic MPS → optimized Metal kernels = **M2-specific acceleration**
4. **Memory layout:** PyTorch tensors → GGUF format = **cache-friendly access**

## 📝 Notes & Observations

### **Technical Insights**

1. **Quantization Quality:**
   - Q4_0 quantization has minimal quality impact
   - Responses remain coherent and relevant
   - Trade-off heavily favors speed over marginal quality loss

2. **Metal Acceleration:**
   - M2 Mac Metal backend is well-optimized for llama.cpp
   - bf16 kernel warnings are harmless (fallback works fine)
   - Native optimization > generic GPU acceleration

3. **Memory Mapping:**
   - llama.cpp uses memory-mapped files
   - Faster load times despite larger model files
   - Better memory management for multiple models

### **Research Implications**

1. **Offline Deployment Viability:**

   - No cloud dependency = practical for EFL applications
   - Latency suitable for interactive tutoring

2. **Intervention Compatibility:**
